## 0. 先回答三个问题

| 问题 | 结论 |
|---|---|
| **架构怎么设计** | 不是「多开几个 Agent」，而是把**调度 / 执行 / 裁决**三者彻底隔离的七层架构 + 三条横切支柱。核心是两个闭环：验证失败有限返工、抽样不合格回流成**环境规则**（不是提示词）。 |
| **技术栈怎么选** | 分两套：**个人单机最小可跑**（Postgres + DBOS + PydanticAI/Claude Agent SDK + Docker 隔离，一台机器今晚能跑）与**团队生产级**（Temporal + MCP 网关 + Kata/gVisor + Langfuse，K8s）。Agent SDK 是「脑」，durable runtime 是「脊」，别让 SDK 假装自己是调度器。 |
| **GitHub 有现成底座吗** | **有零件，没有整车。** 方法论原型是 `cursor/plugins/pstack`（MIT，验证协议源码级可用）；最像「虚拟工程团队」的是 `garrytan/gstack`（MIT，140,815★，已抽查核实）；OpenAI 官方有 `openai/symphony`（Apache-2.0，spec + Elixir 参考实现）。但**没有任何一个项目实现「一手上下文不可变 + 独立裁决 + 可回放因果链 + 错误回流成护栏」这条完整链**，这四块必须自研，也正是护城河。 |

一个必须先接受的反面证据：`varun1505/awesome-software-factories` README 原文写明 —— **"Horthy ran a real lights-off factory for three months in 2025 and abandoned it because the codebase degraded, which is why most teams below run light factories."**（已直取核实）。所以本设计默认做 **light factory**：人在规格/架构上游把关 + 次日抽样，不建议一步到位做「无人读 diff」的 dark factory。

## 1. 设计原则（每条都有一手出处）

| # | 原则 | 出处（已核实原文） |
|---|---|---|
| P1 | **总厨不下场** | pstack `orchestrate.md`："**You run the program, never the code.**"、"**You never author or edit code.**" |
| P2 | **裁决与作者分离** | 同上："**Each PR gets a verifier that isn't its author, on a different model family.**"、"**Green CI is an input to a verdict, not a verdict.**"、"**A verdict covers one head SHA, so a new push needs a new verdict.**" |
| P3 | **单元先写清证据** | 同上："**Each kickoff names the evidence that proves the work is done**… If you can't name the evidence, the unit isn't scoped yet."；"**Start with one unit**… before you fan out" |
| P4 | **验证必须驱动真实应用** | pstack `create-verification-skill/SKILL.md`（raw 源码直取）六段式：Launch / Doctor / Drive / Evidence / Cleanup / Helpers；证据须走真实用户路径、验副作用、cleanup 后证据必须存活；"**A generated skill that was never executed is a draft, not a deliverable.**" |
| P5 | **错误改成结构，不改文字** | pstack `principle-encode-lessons-in-structure`："**Encode the rule as a lint, metadata flag, runtime check, or script instead of more text.**"；注意 pstack 只给了这句 prose，**没给自动生成 lint 的工具** —— 这是必须补的洞 |
| P6 | **先跑通一个单元再 fan out** | pstack `orchestrate.md`："a flaw in the kickoff costs one agent instead of fifty" |
| P7 | **回放 ≠ 重跑** | LLM 非输入纯函数；恢复/审计必须读 journal 快照，重新调模型会重构出一条从未发生过的状态链（Replay Divergence） |
| P8 | **最小 agency + 分级隔离** | OWASP Agentic Top 10 2026 的 ASI02 工具滥用 / ASI06 记忆与上下文投毒；不可逆动作强制人工门 |

## 2. 分层架构

```
L0 接入 Inbox          → L1 上下文 Context → L2 调度 Chief of Staff
                                              ↓
L5 抽样验收 Sampling ← L4 独立验证 Verifier ← L3 执行 Workers
        ↓
L6 环境护栏 Guardrails（贯穿全层，规则库 + 变异测试）

横切：A 事件与状态（append-only log）｜B 观测与成本（OTel）｜C 安全与治理
```

### L0 接入层 · Listener / Inbox
- **职责**：邮件、群聊、工单、GitHub issue、定时触发器 → 标准化 `TaskIntent`。
- **硬机制**：验签用 **raw bytes**（不重新序列化 JSON）+ 常量时间比较 + 时间戳窗口防重放 → **写 inbox 表（`event_id` 主键，单条 INSERT 原子占位）→ 立刻返回 200 → 异步处理**。GitHub 要求 10s 内 2xx；慢活绝不放在 handler。
- **去重键**：GitHub `X-GitHub-Delivery`（手动重发复用同一 ID）、Slack `event_id`、Linear `Linear-Delivery`、Stripe `evt_xxx`（不要用 `data.object.id`）；飞书/企业微信多为 `HTTP Request` 节点打群机器人 webhook，签名 HMAC-SHA256 要自己算，去重键需自建。
- **DLQ + 对账**：webhook 是 at-least-once，把它当「提示」而非「真相」；去重键保留期长于最长重试窗口（Stripe 约 3 天，留一周）；定期按 provider API 回补。
- **输出**：`TaskIntent { intent, source_refs[], risk_level, budget, evidence_spec }`，其中 `source_refs` 指向 L1 的一手原文哈希。

### L1 上下文层 · Context Plane（**最容易被做错的一层**）
- **核心判断**：`mem0`（压缩蒸馏）、`Cognee`（`cognify()` 生成摘要）、`Letta`（模型自编辑 memory block）这三个「记忆层」品类**天然与「给源头信息不给二手信息」冲突**。唯一原生把一手原文当一等公民的是 **Graphiti 的 episode**（"Raw data as ingested — the ground truth stream. Every derived fact traces back here." + bi-temporal 有效性窗口、失效不删除）。
- **必须自研的四条**：
  1. `source_document` 表 **append-only**：原始字节 + SHA-256 + `source_system` / `source_uri` / `message_id` + `occurred_at` / `ingested_at` 双时间戳，写后不可改；大对象存对象存储，表内只存引用。
  2. **摘要/实体/向量与原文物理分离**：派生数据一律带 `source_ref` 外键；**摘要只用于检索排序，不进入 worker 上下文**。
  3. **检索工具只回带引用 + 原文**：把一手库暴露成可限流、返回 `source_hash` 而非改写段落的 tool；这就是「让 AI 自行搜寻上下文」的工程形态。
  4. worker 输出、trace、抽样验收全部引用同一个 `source_hash`，作为因果链锚点。
- `AGENTS.md` / `CLAUDE.md` / skills 属于**上下文，不是护栏**：是 prose，会被忽略且每 session 耗 token。护栏在 L6。

### L2 调度层 · Chief of Staff（**第一处必须自研的核心**）
- **只读约束**：不写交付物、不改代码、不「顺手帮忙修一下」；状态只记在 durable workflow + 项目 tracker。
- **职责**：任务分级与 worker 能力注册/路由 → 拆成「可验证单元」→ kickoff 写明目标、可写/不可写路径、禁止动作、**可验证证据规格** → fan-out / fan-in / 超时 / 部分失败 → 预算、并发、熔断、夜间触发。
- **拓扑**（照 pstack，别自己发明）：一个单元一个 owner；每个独立任务开**全新 worker**且互相不可见；只在某区域 worker 很多时设 sub-coordinator；**最多三层**（你 → sub-coordinator → worker），每个 coordinator 约 10 个在飞，完成一个补一个不等整批。
- **人的介入点**：只在不可逆动作、产品偏好、真死胡同时升级；重试、CI 抖动、rebase 一律不打扰人。

### L3 执行层 · Workers
- 领域 Agent（research / code / doc / data / ops），每任务一个干净环境。
- **隔离分级**（成本可控的关键）：`git worktree`（只解决并行写冲突，**零隔离**）+ 每任务一个 Docker 容器（只读根 fs、临时卷、网络白名单、CPU/内存限额、短期注入凭据）；**只在 verifier 要跑 worker 产出的不可信代码时**升级到 gVisor / Kata / Firecracker，不要全链路上 microVM。
- 工具统一经 MCP 网关，**per-call 带参数授权**，凭据由网关托管并短期注入，绝不进 agent 代码。工具白名单 ≠ 授权：同一个 `run_query` 可能是 SELECT 也可能是 DROP TABLE。
- worker 可以自证，但**自证不构成 verdict**。

### L4 验证层 · Independent Verifier（**第二处必须自研的核心**）
- **holdout 设计**（抄 `aberson/void-furnace` 的思路，别抄它的代码）：verifier 的输入结构体只接受 `issue body + diff + test output + governance docs`，**把作者的 PR 描述 / title / commit message / plan / tool transcript 结构性排除**，并用函数签名 + AST guard + 单测锁死这个形状，防止后人「不小心」放宽。这直接治 LLM-as-judge 被 coder 自述污染。
- **verifier 与作者不同模型家族**；每个产物一个 verifier；verdict 绑定 `artifact_hash` / `head_sha`，**一次 push 作废重判**。
- **六段式 verify skill**（直接复用 pstack 协议，MIT）：Launch（ready = usable，不是进程有响应）/ Doctor（只读体检）/ Drive（真实 selector，禁止坐标与 tab 顺序）/ Evidence（真实用户路径、动作+结果状态成对、验副作用、dry-run 要实测跳过了什么）/ Cleanup（只 kill 自己起的，**绝不删证据**）/ Helpers（可执行且调用写在正文）。
- **feature map**：`features/README.md` + 每个用户可见功能一个文件，四个固定 H2；「Never weaken the journey to make it pass」；配 `maintain-verification-skill` 定期巡检防地图腐烂。
- **门禁组合**：确定性检查（lint / 类型 / 测试 / 架构约束）→ 行为验证（真跑应用）→ LLM-as-judge（只作补充）→ **变异测试证明每条门禁真的会触发**（抄 `nicolasmelo1/software-factory` 的做法：规则双写，一次 prose 说 why、一次 check 会 fail，且每个 check 有一个 mutation 证明它开火）。
- **返工**：FAIL 回到 L3，上限 N 次（pstack 建议 2 次后 drop 单元并 replan），仍失败升级人工。

### L5 交付与验收层 · Delivery & Sampling
- 产物 + 不可变证据包落库；**抽样策略**：全量覆盖异常/拒绝/负反馈/成本异常，其余按任务类型分层随机。
- **只读回放视图**：按 `run_id` 从 append-only `events` 表重建完整因果链 —— 需求事件 ID → `source_hash[]` → `prompt_hash` + `model_version` + 采样参数 + semconv 版本 → 每步工具参数与**结果快照** → verifier 判定与依据 → `artifact_hash` → 抽样结论。
- **三种重放严格分开**：恢复重放（读 journal，绝不重新调模型）/ 审计重放（只读、带身份与版本戳）/ 评测重放（新模型跑旧 case，diff 后单独存，绝不覆盖原状态）。
- 不合格 → 归因「上下文没给透」还是「验证规则有洞」还是「环境约束缺失」→ 写回 L6。

### L6 环境护栏层（贯穿，不是最后一步）
- 规则形态：ast-grep YAML 规则、类型约束、目录约定、JSON Schema、模板、`verify-*` skill、protected-files allowlist。
- 每条规则带 `mutation_test_ref`：**故意破坏的变体上必须展示 property 真的会失败**，否则门禁形同虚设。
- 这就是视频里「改规则一劳永逸」的真实落点，也是与原始访谈一致、而与视频口播不同的那一层（详见上一轮报告的事实核查）。

### 三条横切支柱
- **A 事件与状态**：append-only `events` 是**恢复与审计同源**的唯一真相。Temporal 官方文档明确 Event History 既是崩溃恢复依据又「serves as an audit log」，并有 Reset 与 Principal Attribution（服务端盖章，客户端不可伪造）。执行日志（完整、不可变、长期）与 observability trace（可采样、可脱敏）**必须分成两套**，别把 trace 当唯一记录。
- **B 观测与成本**：OpenLLMetry + `gen_ai.*` semconv 埋点；`prompt_hash` 不是任何标准字段，自己算 SHA-256 写自定义 span attribute；OTel GenAI 约定仍处 Development、无 tagged release，**必须记录本次用的是哪版约定**（pin commit），否则半年后回放读不懂。成本 = token × **版本化价格表**，按 `task_id` 等业务标签归因。
- **C 安全与治理**：最小权限、工具运行时不可新建、不可逆动作人工门、密钥不进 agent、间接注入的架构性防护（untrusted 内容与 privileged 工具分离）、写持久记忆前验证事实（防 ASI06 投毒）、每会话动作数/成本上限 + 熔断。

## 3. 状态机与数据模型

### 状态流转
```
INBOX_RECEIVED → NORMALIZED → SCOPED(evidence_spec) → DISPATCHED
→ IN_PROGRESS → SELF_CHECKED → VERIFYING → VERDICT{PASS|FAIL}
   ├ FAIL 且 retries<N → DISPATCHED（新 worker，全新上下文）
   └ FAIL 且 retries≥N → NEEDS_HUMAN
VERDICT:PASS → DELIVERED → SAMPLED → ACCEPTED | REWORK→RULE_UPDATED
旁路：BLOCKED_NEEDS_HUMAN / BUDGET_EXCEEDED / TIMEOUT / CANCELLED
```

### 核心表（Postgres 单库即可起步）
| 表 | 关键字段 | 约束 |
|---|---|---|
| `inbox_event` | `event_id` PK, source, signature_ok, payload_hash, received_at, status | 单条 INSERT 原子占位 |
| `source_document` | `source_hash` PK, source_system, source_uri, raw_ref, occurred_at, ingested_at | **append-only，禁 UPDATE/DELETE** |
| `task` | task_id, parent_id, intent, `source_refs[]`, `evidence_spec`, risk_level, budget, status | evidence_spec 为空不得派发 |
| `agent_run` | run_id, task_id, actor, `model_family`, `model_version`, `prompt_hash`, `semconv_version`, tool_policy | verifier 的 model_family ≠ author |
| `event` | seq, run_id, type, actor, payload_json, `idempotency_key`, side_effect_receipt, `hash_chain` | append-only + 哈希链 |
| `artifact` | artifact_hash, run_id, path, produced_at | 不可变 |
| `verdict` | verdict_id, run_id, verifier_run_id, `head_sha`, checks[], evidence_refs[], result | 新 push 自动作废 |
| `sample_review` | review_id, run_id, reviewer, outcome, root_cause, rule_ref | 必须指向一条规则或上下文修正 |
| `guardrail_rule` | rule_id, kind, target, `mutation_test_ref`, version, enabled | 无 mutation 证明不得启用 |

### 统一事件信封（自研契约）
`run_id / task_id / parent_id / actor / tool / args_hash / model_version / prompt_hash / artifact_hash / approval_principal / idempotency_key / side_effect_receipt / semconv_version`

> 引擎只给你「记录位置」，不给语义。跨引擎幂等键分配、副作用凭据登记、防 Replay Divergence 纪律都要自己定。

## 4. 技术栈选型

### 栈 A · 个人单机最小可跑（目标：本周跑通一个单元）

| 层 | 选型 | License | 理由 / 代价 |
|---|---|---|---|
| 语言 | Python 3.12+（或 TypeScript 二选一） | — | 生态与 SDK 最全 |
| 状态/队列/审计 | **Postgres 16 + pgvector + 自建 append-only `events` 表** | PostgreSQL | 状态、队列、审计、向量同库同事务 |
| Durable runtime | **DBOS Transact**（`dbos-inc/dbos-transact-ts`，纯库；Python 实现同系列） | MIT | 只需 Postgres；`@DBOS.step()` 检查点、`recv/send` 即审批门、内置 durable queue + cron；无独立服务 |
| Agent SDK | **PydanticAI**（官方支持 DBOSDurability）或 **Claude Agent SDK Python** | 均 MIT | SDK 是「脑」，不要它做调度 |
| 模型入口 | **LiteLLM 核心**（单进程 proxy） | MIT（核心），`enterprise/` 另算 | 统一供应商、成本、限流 |
| 工具层 | 官方 MCP SDK + **docker/mcp-gateway** | MIT | profile 级工具开关、每 server 独立容器 |
| 需求接入 | **Activepieces**（MIT core）或 n8n（内部自用合规）+ 自研 inbox 去重表 | MIT / SUL | 见 §7 License 陷阱 |
| 隔离 | git worktree + Docker（只读根 fs / 网络白名单 / 资源限额） | Apache-2.0 | 成本最低的「干净环境」 |
| 验证 | **pstack `create-verification-skill` 协议** + **promptfoo** + **ast-grep** | 均 MIT | 直接抄六段式，别自己发明 |
| 观测 | OpenLLMetry → Langfuse OSS（或先落本地 Parquet） | Apache-2.0 / MIT core | 保住后端可替换 |
| 密钥 | **SOPS** | MPL-2.0 | 无服务端，单机最省 |
| 角色配置 | 借用 **gstack** 角色 slash commands 或 pstack `orchestrate.md` | MIT | 快速起步，但绑 harness |
| 部署 | Docker Compose，一台机器 | — | 不上 K8s、不上 Temporal |

> 单机**不要**上 Temporal（生产自托管要 4 个服务角色 + visibility 库）、**不要**用 Trigger.dev 自托管（官方自述 compose 不足以生产、worker 需 4 vCPU/8GB）、**慎选** Inngest（SSPL 尾巴）。

### 栈 B · 团队生产级

| 层 | 选型 | License | 理由 / 代价 |
|---|---|---|---|
| 状态/恢复/审计 | **Temporal**（K8s 自托管或 Cloud）+ PydanticAI `TemporalDurability` | MIT | 确定性重放、Signal/Query/Update、Event History 兼审计、Reset、Principal Attribution |
| 省运维备选 | **Restate**（单二进制，BSL 1.1）或 **Hatchet**（MIT，Postgres，durable event wait + CEL） | BSL / MIT | 前者省外置 DB，后者 License 最干净 |
| 事件总线 | Postgres 事件表打底 + **NATS**（低延迟）或 **Kafka**（长期可重放）；Redis 只放热状态 | Apache-2.0 | 执行日志长期留存 |
| 上下文 | **Graphiti**（episode 谱系）+ Neo4j/FalkorDB + pgvector/Qdrant + **自研一手原文不可变存储** | Apache-2.0 | 要自运图库 |
| 模型/工具治理 | LiteLLM + **IBM ContextForge** 或 **agentgateway** + 私有 MCP Registry | Apache-2.0 | CEL/OPA per-call 授权、凭据网关托管、OTel 审计 |
| 隔离 | **Kata / Firecracker**（verifier 跑不可信代码），gVisor 折中，其余 Docker | Apache-2.0 | 按步骤分级隔离控成本 |
| 验证门禁 | pstack 协议 + promptfoo + SWE-bench 式 harness + **reviewdog**（门禁结果回 PR）+ **github/gh-aw**（safe outputs 白名单） | 多为 MIT | 门禁要出现在 agent 看得见的地方 |
| 观测 | OpenLLMetry + `gen_ai.*` → Langfuse（MIT core）+ ClickHouse | MIT / Apache-2.0 | RBAC/审计日志/保留策略是 EE 模块 |
| 密钥 | **Infisical**（MIT core，含 Agent Vault）或 **OpenBao**（MPL-2.0） | MIT / MPL-2.0 | 避开 Vault 的 BUSL 1.1 |
| 安全 | NeMo Guardrails + OWASP LLM Top 10 2026 / Agentic Top 10 2026 checklist | Apache-2.0 / 开放文档 | 注入只能架构性防护 |

### 关键取舍速查
| 抉择 | 选左边 | 选右边 |
|---|---|---|
| Temporal vs DBOS | 需跨语言确定性重放、完整审计、专职运维 | 单机零运维、只需长时可恢复 |
| n8n vs Activepieces | 连接器最多、内部自用 | 要嵌入产品 / 要干净 License |
| Langfuse vs Phoenix | MIT core、可自托管 | **注意 Phoenix 实为 Elastic License 2.0**，禁止对外托管（已直取 LICENSE 核实，网上多误标 Apache-2.0） |

## 7. 落地路线（严格按「先跑通一个单元再 fan out」）

| 阶段 | 目标 | 验收判据 |
|---|---|---|
| **P0 骨架** | Postgres + DBOS + 1 个 worker + 1 个 verifier，跑通**一个**只读任务 | 能从 `events` 表按 run_id 还原这次决策；verifier 与 worker 不同模型家族 |
| **P1 接入与上下文** | inbox 去重表、验签、一手原文表、检索工具 | 同一 webhook 重发不产生第二个任务；worker 拿到的是原文 + hash，不是摘要 |
| **P2 验证闭环** | 六段式 verify skill 生成器、feature map、holdout verifier、verdict 绑定 hash | 故意破坏一个变体，门禁必须开火；push 新 commit 后旧 verdict 自动作废 |
| **P3 抽样与规则回流** | 回放视图、抽样策略、错误→lint rule + 变异测试 | 一次抽样不合格能产出一条带 mutation test 的规则，且同类错误不再复现 |
| **P4 夜间无人值守（light factory）** | 预算/熔断/不可逆动作人工门、夜间触发、升级链 | 连续一周夜间运行无预算失控、无未授权副作用；再评估是否升 dark |

> 每一阶段的退出条件都是「证据」，不是「看起来能跑」。这正是 pstack `autonomous-run.md` 的核心：把「完成」定义为**可检查谓词**，且「A plateau is not a stop… never relax the predicate to declare victory.」

### P0 实现状态（2026-11-09 已落地）

代码在 `michelin-workbench/`，零外部依赖、零 API key 即可运行：

```
cd michelin-workbench
python3 run.py demo --scenario ok|flaky|always_fail|sampling_reject
python3 run.py replay --run-id <run_id>
python3 run.py verify-chain
python3 -m unittest discover -s tests -v     # 28 项全绿
```

已实现的六层切片：`platform/`（append-only events + 全局哈希链 + 统一信封 + 幂等契约）、`context/`（一手原文 append-only，刻意无摘要能力）、`chief/`（领域状态机 + 只读总厨）、`workers/`（每任务全新上下文）、`verification/`（holdout 结构体 + AST 签名锁 + 独立重跑门禁 + 跨模型家族裁决 + 变异测试）、`delivery/`（只读回放 + 抽样 → 规则回流）、`guardrails/`（无 mutation 证明不得启用）。

**与本节选型表的一处诚实偏差**：为让 P0 今天就能跑，脊用 **SQLite**（Python 标准库）而非 Postgres + DBOS，模型用确定性 `ScriptedModel` 而非真模型。二者都留了接缝 —— `EventStore` 的方法签名即 Postgres 适配器契约（`compose.yaml` 已备好 pgvector/pg16），`ModelAdapter` 协议可切 `openai_compat`（`MW_MODEL_BACKEND` / `MW_API_KEY`）。**P0 没有实现 durable execution 与崩溃恢复**，进程内循环只是状态机的载体，这一层必须在 P1 换成 DBOS/Temporal 后再谈夜间无人值守。

P0 验收判据实测结果：六类锚点齐全、按 `run_id` 可还原决策（含 `source_hashes → prompt_hash → model_version → artifact_hash → verdict → 抽样结论`）、worker=anthropic / verifier=openai 不同家族、98 条事件全局哈希链完好；`always_fail` 3 次后升级人工，`sampling_reject` 产出一条 `enabled=True` 且带 `mutation_test_ref` 的环境规则。

落地过程中发现并修复一个真问题：自动幂等键若只由信封派生，会把「第 2 次派发」和「后续每次状态迁移」误判为崩溃重放而吞掉，证据链凭空缺段。最终契约定为 `SHA256(调用方 key || 本次 payload)`，并写回信封保证审计与存储一致。

### P1 实现状态（2026-11-09 已落地，实库验证）

**环境**：Docker 容器 `michelin-p1-pg`（`pgvector/pgvector:pg16`，PG 16.15 + pgvector 0.8.6，映射 `127.0.0.1:55432`，刻意避开用户已有的 5434 端口容器）；项目内 `.venv` 安装 psycopg 3.3.8 + **DBOS 3.4.0（MIT，2026-10-28 发布）**。DBOS 的 `DBOSConfig` 字段与 `send/recv/start_workflow/SetWorkflowID` 签名均经 PyPI、官方文档与运行时 introspection 三重核实。

**已交付三块**：

1. **持久化脊**：`EventStoreProtocol` 显式契约 + `PostgresEventStore`（PL/pgSQL trigger 强制 append-only、`pg_advisory_xact_lock` 串行化哈希链、BIGSERIAL、`ON CONFLICT DO NOTHING` 幂等）。P0 的 `ChiefOfStaff` / verifier / replay / sampler **一行未改**即可切到 Postgres——接缝设计得到实证。
2. **L0 接入层**：`inbox/` 包。raw bytes HMAC（GitHub / Slack v0 / 自建三种方案）、`compare_digest` 常量时间、时间戳窗口防重放、**单条 INSERT 原子占位去重 → 立刻 200 → 线程池异步处理**、`inbox_delivery` 台账 + DLQ + `reconcile()` 对账、原始投递存对象存储只留 `raw_ref`、标准化时把**原始 JSON 全文**作为一手原文交给 worker。
3. **Durable workflow**：`chief/durable_workflow.py`。5 个 `@DBOS.step()` 检查点 + `DBOS.recv/send` 人工审批门 + `SetWorkflowID(delivery_id)` 做 exactly-once。所有非确定性动作（生成 ID、调模型、写事件）都关在 step 内，workflow 体只做编排，落实「恢复重放绝不重新调模型」。

**关键验收数据**：
- 硬崩溃演示：`MW_CRASH_STEP=execute` 在 `step_execute` 内 `os._exit(137)`；新进程 `DBOS.launch()` 自动恢复。恢复后该 run 的 `intent.received=1` / `task.scoped=1` / `worker.model_response=1`，证明已完成 step 被跳过、模型未被重复调用；20 条事件、六锚点齐全、哈希链完好、审批门 `DECIDED/APPROVED`。
- 同一 webhook 重发：`replay_count=1`、`task` 表仍只有 1 行、仅 1 条 `inbox.linked`；坏签名 401 且**不占用真实 delivery_id**（后续合法投递仍成功）；过期时间戳 401；下游故障进 DLQ 后 `retry_dlq` 从对象存储取回原文重放成功。
- 全量回归：系统 Python（零依赖路径）48 项中 40 通过 / 8 项按环境 skip；`.venv` 全量 **48/48 通过**（含真实 Postgres 与跨进程 DBOS 崩溃恢复，临时库自动创建销毁）。

**踩到并解决的两个真实约束**：① DBOS 同一系统库里 `application_version` **跨应用必须唯一**，探测脚本占用的 `0.1.0` 导致正式应用启动失败 → 改为 `michelin-p1-0.1.0`，且 start/resume 必须用相同版本戳才会接管 PENDING workflow；② `DBOS.recv` 的参数名是 `timeout_seconds`（README 示例写的是 `timeout`，已过时）。

**P1 之后仍未做**（别把骨架当成生产系统）：真实模型与 MCP 网关、每任务 Docker/gVisor 隔离、OTel GenAI 埋点与 Langfuse、durable queue 的并发/限流（当前只用 `start_workflow`）、夜间 cron 与预算熔断、fan-out/fan-in、webhook HTTP server 目前是标准库最小实现（生产应换 ASGI + 反代）。另外 `application_version` 变更时的**工作流版本迁移**尚未处理，升级前需查 DBOS 的 `fork_workflow` / patching 机制。其中「六段式 verify skill 生成器 + feature map + 真实 git diff/worktree」已在下一节的 P2 落地。

### P2 实现状态（2026-11-09 已落地，真实 git + 真实 CLI 验证）

#### 运行时护栏：只承诺真正强制了的边界

`src/michelin/runtime/` 四个模块做成外层包装，不改 P3Pipeline：

| 模块 | 落地内容 |
|---|---|
| `sandbox.py` | env 白名单（宿主密钥 / DSN / token 一律不进子进程）、`HOME`/`TMPDIR` 指向沙箱、只读源快照（内容指纹）、`RLIMIT_CPU/AS/FSIZE/NOFILE`、wall-clock 超时按进程组 SIGKILL；`container_command()` 生成 `--network=none --read-only --cap-drop=ALL` 的生产接缝 |

#### 最重要的一处设计冲突：holdout 的「跨模型家族」要求

pstack 的硬约束是「verifier 与作者分属**不同模型家族**」。DeepSeek 的两个模型

- `ChiefOfStaff.__init__` 直接 `RuntimeError`；
- `IndependentVerifier.verify` 直接 `HoldoutViolation`。

**两种处理方式都不可接受**：① 悄悄放宽护栏 —— holdout 保证就此消失且无人察觉；

- 默认仍然拒绝（护栏的默认行为一个字没改，`tests/test_holdout.py` 的


**脚本模型路径一直没暴露它**，因为脚本输出是「将税率改为 TAX_RATE = 0.06。」
—— 数值后面紧跟句号而不是换行。只有真实模型会把整段代码贴回来，才会踩到。
这正是「先让真实模型干活」的收益：它替你撞出了确定性测试照不到的死角。

修法有两条，缺一不可：
1. 正则**不能**在数值后加 `\s*`；百分号检测单独做（`_has_percent_suffix`）。
2. 加回归测试锁死「替换后行数不变 + 语法有效 + 百分号识别 + 大数值拒绝」。

#### 顺手补的两处稳健性

- **产出不可机械检查 → 返工，而不是崩流水线**：模型可能回 `TAX_RATE = 6%`、
  可能回整段文件、可能回一句没有赋值行的话。以前这会 `raise ValueError` 让整条
  run 崩掉；现在抛 `WorkerOutputError`，总厨记 `worker.output_rejected` 事件，
  换**全新 worker + 全新 worktree** 重来，返工耗尽才升级人工。
- **不给真实模型注入答案**：`_with_rate()` 以前会给真模型塞一个 `_p2_target_rate`
  属性（其实从没被读过）。现在真模型**完全靠推导**——把目标值塞进 prompt 会让
  「模型真的在改代码」变成「照抄答案」，那条路径就没有验证价值了。

#### P2 也要记豁免

`P2Pipeline` 与 `BehaviorVerifier` 同样有家族护栏，同样改成「默认拒绝 + 显式
豁免 + 豁免入链」：`model.independence_waived` 事件在链的第 2 条，verdict 的
checks 含 `model_independence_waived`，`verdict.issued` 带 `independence_waiver`。

#### 门禁：真实模型冒烟现在验两件事

`real_model_smoke` 从「能连通」升级为「连通 **且** 能产出 P2 worker 需要的
可机械检查格式」：

```
deepseek-flash 调用成功：67 tokens ...；P2 输出格式探针通过（TAX_RATE = 0.06）
```

第二问用真实模型要一次 `TAX_RATE = <小数>`，并校验：能解析、不带百分号、
数值 ≤ 1。**连通性通过不代表输出格式可用** —— 这一问才是真正会红的那一问。

#### 现状与边界

- 真实模型接在 P0（只读分析）与 P2（改代码）两条链路；P3 的仓库访谈与
  自动起草仍是确定性实现。
- P2 的可写范围目前只有一个文件（`shop/pricing.py`）；多文件、多轮编辑、
  模型自己决定改哪些文件尚未做。
- 真实模型的裁决仍是「独立重跑 + 变异门禁」说了算，LLM judge 只作补充意见
  （`kind=advisory`），不参与通过判定。

### 7.10 P7：多文件编辑 —— 模型自己决定改哪些文件（2026-11-10）

**结论**：DeepSeek 在真实 git worktree 里**自己读文件、自己决定改哪些文件**，
独立 verifier 在另一个干净 worktree 上重放多文件 diff 并用**两条 Drive 断言**判定，
裁决 PASS。

```
模型读了    : ['shop/pricing.py', 'shop/cli.py', 'README.md']
模型改了    : ['shop/pricing.py', 'shop/cli.py']
真实用量    : worker in=1561 out=706（reasoning=227）· verifier in=592 out=1614
              合计 2153 in / 2320 out ≈ $0.0413，3 次外部请求，耗时 47.9s
结果        : ACCEPTED / PASS，skill PROVEN，变异门禁 6/6 全开火，24 条事件，六锚点齐全
```

模型写出的 diff（**注意它的改法是自己想的**）：

```diff
-from .pricing import total_price, format_amount
+from .pricing import TAX_RATE, total_price, format_amount
-        print(f"SHOP_READY version={VERSION}")
+        print(f"SHOP_READY version={VERSION} rate={format_amount(TAX_RATE)}")
-TAX_RATE = 0.10
+TAX_RATE = 0.06
```

它没有硬编码 `:.2f`，而是**复用了仓库里已有的 `format_amount`** —— 这是把
「给 AI 手和眼」贯彻到底的收益：模型拿到的是真实的代码，不是被裁剪过的片段。

#### 三件新增的东西

1. **有界工具循环**（`src/michelin/workers/editing_worker.py`）。模型可以
   `READ <路径>` 看文件，再 `=== BEGIN FILE: <路径> === … === END FILE ===`
   提交编辑。轮数上限 `max_rounds`（默认 6）—— **没有轮数上限的工具循环就是
   「烧钱不设防」**，每一轮都是一次真实计费调用。
2. **可写范围是硬约束**。总厨划定 `shop/**`，模型越界即被拒（不是提醒）。
   同时防路径穿越（`..`、绝对路径）与读越界。越界动作会记进
   `worker.output_rejected`，在证据链里看得见。
3. **多条 Drive 断言**（`SkillSpec.extra_drive_checks`）。**这是「多文件」能被
   验证的关键**：只有一条断言时，模型只改一个文件也能通过，多文件就形同虚设。
   现在两条断言各管一个文件（total 金额 → pricing.py；doctor 报税率 → cli.py），
   并且**新增的那条断言也有对应变异体**（`doctor_missing_rate`），变异门禁
   从 5 条变 6 条，全开火才算数。

#### 产出仍然是机器可查的

模型给的是「文件 → 完整新内容」，**写文件与 diff 由确定性 git 完成**。解析必须
严格：块不成对、路径越界、内容语法错误，一律判为「产出不可机械检查」，换**全新
worker + 全新 worktree** 重来，不猜作者想干嘛。

#### 这一轮最重要的一次修复：变异门禁被「陈旧字节码」静默架空

P7 推上远端后，**真实 CI（ubuntu）第一次跑就红了**：`unit_suite` 两项失败，
`all_fired=False`。而本机（macOS）154 项全绿 —— 又一次平台/时序差异。

用 Docker 拉起 Linux 容器复现后，挖到根因（`wrong_tax_rate` 变异体
「没开火」，而它恰好是唯一**改动长度相同**的那个：0.06 → 0.10）：

```
变异后 pricing.py: 'TAX_RATE = 0.10'
变异后运行 stdout: TOTAL=31.80          ← 变异根本没生效
加载位置: .../shop/pricing.py TAX_RATE 0.06   ← 加载的是陈旧字节码
```

**机制**：`.pyc` 头部记录的是源文件的 **mtime（秒级）+ size**。`.pyc` 里
缓存的判定就是「size 相同 且 mtime 相同（秒级）→ 缓存有效」。而
「同长度改动 + 同一秒内重写」同时满足这两个条件 → Python **复用陈旧字节码** →
**故意改坏的版本根本没被加载** → Drive 依然通过 → 变异体「没开火」。

我原先一直以为 `-S` 会禁止写字节码 —— **错**。`-S` 只是跳过 `site` 模块，
**照样写 `.pyc`**；真正管用的是 `PYTHONDONTWRITEBYTECODE=1` / `-B`。

这个 bug 的严重性远超「一个测试挂掉」：**它能让变异门禁在没有变异体的情况下
判绿** —— 也就是「门禁形同虚设」最字面的形态。而且它是**时序相关**的：
macOS 本机跑得慢、mtime 跨秒，所以本地永远绿；CI runner 快，就踩中。
P2 的 `wrong_tax_rate` 同样是同长度变异，**一直在靠运气躲过**。

修法两道防线：
1. 生成的 helper 里 `env["PYTHONDONTWRITEBYTECODE"] = "1"`（连同 P3 的通用
   helper 一起）—— 根本不写 `.pyc`；
2. 变异 harness 在每次 probe 前 `_clear_bytecode(tree)` 删掉已存在的 `__pycache__`。

并补了一条**专门锁死这个陷阱**的回归测试：同长度改写后必须真的生效
（`TOTAL=31.80` → `TOTAL=33.00`）。现在本机与 Linux 容器都通过。

> 教训：**「变异门禁全开火」这个结论，必须自己证明变异体真的被加载了**，
> 否则「没开火」和「根本没生效」是分不清的。

#### 顺手修掉的几个坑

1. **变异套件的干净基线是写死的** P2 版本 → 多文件场景的基线本身不绿，
   变异门禁误判为「没全开火」。修法：`baseline_files` 与 `mutations` 都参数化，
   多文件场景用 `CLI_SOURCE_MULTI` + `MUTATIONS_MULTI`。
2. **`_with_rate()` 会覆盖 ScriptedModel 的脚本** —— 它是单文件 worker 专用的。
   多文件 worker 必须完全靠推导（把目标值塞进 prompt 会让「模型真的在改代码」
   退化成「照抄答案」）。现在只在 `worker_factory is None` 时才注入。
3. **`MeteredModel` 只包了单轮调用**，多轮工具循环直接 `AttributeError`。
   现在 `complete_chat` 也计量。

#### 门禁：`real_model_smoke` 升级成三问

1. 连通性 + 真实用量；
2. 能否产出 P2 worker 需要的可机械检查格式（`TAX_RATE = <小数>`）；
3. 能否按多文件 EDIT 协议产出可解析的编辑块。

第 3 问现在实测通过（`P7 EDIT 协议探针通过（['shop/pricing.py']）`）。
**协议不通用 = 多文件路径不可用**，这一问才是真正会红的那一问。

#### 还有一个只有真实模型才会暴露的问题：门禁不能是随机的

本机门禁出现过一次 `real_model_smoke` 失败，但三段探针的 summary 都写着「通过」。
查证据才发现：第一问用了 `max_tokens=32`，而**推理模型会先把这 32 个 token
花在 reasoning 上**（`reasoning_tokens=32`），于是**正文为空**，`ok=False`。
这次推理短就过、下次推理长就挂 —— **一个概率性失败的门禁等于没有门禁**。

修法：探针预算给足（32 → 256 / 128 → 512），并把「空正文」与「模型没答」分成
两种可诊断的失败（`finish_reason=length` + `reasoning=N` 会直接写进证据）。
连跑 4 次确认不再随机翻车。

> 这是「真实模型路径」的第三个独有坑（前面两个是换行被吃掉、协议不通用）：
> **只有真模型会先消耗推理预算，才会让「正文预算」变成一个概率变量。**

#### 现状与边界

- 多文件编辑目前只在**这条固定任务**上验证过（两个文件）。模型在**陌生仓库**里
  自己定位该改哪些文件的能力还没被测过 —— 那需要 P3 的访谈器与真实模型打通。
- 模型仍然只有 `READ` 与「提交编辑」两种动作，没有跑测试、没有看报错再改
  （真正的 agentic 循环还没做）。
- 越界拒绝、路径穿越拒绝、内容语法错误拒绝，都只作用于**已声明可写范围**；
  「哪些文件该改」这件事目前仍由总厨在 `writable_paths` 里划好范围。
